# แบบเสนอ: จัดการบัญชีลูกค้าจริงโดยไม่เข้าสู่ระบบ

วันที่: 12 ตุลาคม 2026
สถานะ: ผู้ใช้อนุมัติแบบแล้วด้วยข้อความ “อนุมัติแบบ” วันที่ 12 ตุลาคม 2026; ยังรอทบทวนแผนดำเนินงานและเลือกวิธีทำ ยังไม่เปลี่ยนระบบจริง

## ความต้องการที่ยืนยันแล้ว

ผู้ใช้ยืนยันให้บุคคลทั่วไปเพิ่ม/ลบบัญชีลูกค้าจริงได้โดยไม่มีการยืนยันตัวตน ไม่ใช่ข้อมูลจำลอง ไม่ต้องมีบัญชีหรือบทบาท admin สำหรับการทำรายการนี้ ผู้ใช้รับทราบแล้วว่าบุคคลอื่นหรือบอตอาจลบบัญชีลูกค้าทั้งระบบได้

นี่เป็นงานเปลี่ยนโครงสร้างสิทธิ์ (architectural) เพราะเปลี่ยนขอบเขตการเข้าถึง API ที่มีสิทธิ์จัดการ Supabase Auth ไม่ใช่เพียงเปลี่ยนการแสดงปุ่ม

## แนวทางและข้อแลกเปลี่ยน

1. **เสนอใช้ API สาธารณะเฉพาะงานสมาชิก**: เพิ่ม `public-members` แยกจาก `admin-users` ไม่ตรวจ user JWT หรือบทบาท admin ใน API ใหม่นี้ จำกัดคำสั่งเฉพาะรายชื่อแบบไม่เปิดเผยข้อมูลติดต่อ การเชิญ และการลบสมาชิกจริง รักษาสิทธิ์แก้สินค้าและการอ่านโปรไฟล์ส่วนตัวเดิมไว้
2. เอาการตรวจ Auth/role ออกจาก `admin-users` เดิม: เปลี่ยนโค้ดน้อยกว่า แต่เสี่ยงเปิดเผยอีเมล ชื่อ และเบอร์โทรจาก response เดิม และทำให้สัญญา API ผู้ดูแลเปลี่ยน จึงไม่เสนอใช้
3. ใช้รหัสจัดการเฉพาะร้าน: ลดความเสี่ยงจากบุคคลทั่วไป แต่ไม่ตรงกับคำยืนยันล่าสุดของผู้ใช้ จึงไม่เลือก

ไม่มีแนวทางใดที่เปิดให้บุคคลทั่วไปลบทุกบัญชีแล้วป้องกันบุคคลทั่วไปตั้งใจลบบัญชีได้พร้อมกัน การตรวจรูปแบบข้อมูล, CORS และกล่องยืนยันไม่ใช่การยืนยันตัวตน และไม่ป้องกันผู้เรียก API โดยตรง

## ขอบเขต UI และข้อมูลที่เปิดเผย

- ปุ่มจัดการสมาชิกแสดงบน desktop และมือถือแม้ไม่ได้เข้าสู่ระบบ เมื่อเชื่อมระบบสมาชิกสำเร็จ
- หน้าต่างแสดงคำเตือนชัดเจนว่าจัดการบัญชีจริงและการลบเป็นแบบถาวร
- รายชื่อแสดงรหัสสมาชิก UUID และป้าย `สมาชิก` เท่านั้น ครั้งละ 25 บัญชี ไม่แสดงหรือส่งกลับชื่อจริง อีเมล เบอร์โทร ที่อยู่ referral code หรือข้อมูล session
- การเลือกลบจึงใช้รหัสสมาชิก ไม่ใช่ค้นหาด้วยอีเมล ไม่เพิ่ม email lookup ที่ทำให้ตรวจสอบว่าบุคคลใดเป็นลูกค้าได้
- แบบเพิ่มสมาชิกใช้ชื่อและอีเมลที่ผู้กรอกระบุ ไม่เก็บช่องโทรศัพท์หรือที่อยู่ในแบบสาธารณะ และไม่แสดงค่าที่กรอกต่อคนอื่น
- คง focus trap, Escape, การคืน focus, safe DOM rendering, loading/error/retry และการป้องกัน response เก่าทับหน้าต่างที่เปิดใหม่
- การเข้าสู่ระบบ การกู้รหัสผ่าน และการตรวจยืนยันอีเมลของลูกค้ายังเป็นคนละขั้นตอนกับสิทธิ์ของผู้จัดการสมาชิกแบบสาธารณะ

## API และความหมายของเพิ่ม/ลบ

- `public-members` เป็น Edge Function ใหม่ ใช้ service-role credential ที่มีอยู่เฉพาะ environment ฝั่งเซิร์ฟเวอร์ ห้ามส่ง key นี้ลง frontend/log/response
- เปิด gateway `verify_jwt=false` สำหรับ function ใหม่นี้โดยตั้งใจ และไม่กำหนดว่าผู้เรียกต้องมี session; frontend ใช้ public configuration เท่านั้น
- เซิร์ฟเวอร์มีสวิตช์ `PUBLIC_MEMBERS_ENABLED` ค่าเริ่มต้นปิด ใช้หยุดการเข้าถึงสาธารณะเมื่อจำเป็น สวิตช์นี้ไม่ใช่รหัสที่ผู้ใช้ต้องกรอก
- อนุญาตเฉพาะ POST/OPTIONS, body ไม่เกิน 4096 bytes, ตรวจชนิด input, email, ความยาวชื่อ, UUID และ pagination บนเซิร์ฟเวอร์ อนุญาต origin ของเว็บเดิม แต่ไม่ถือว่า Origin เป็นหลักฐานสิทธิ์
- `list`: ใช้ Auth Admin API แล้วคืนเฉพาะ UUID ของบัญชีที่มีโปรไฟล์สมาชิก MAXMUXSIX; ไม่คืน payload ดิบจาก provider
- `invite`: ใช้ `inviteUserByEmail` เพื่อเพิ่มสมาชิกผ่านคำเชิญ ผู้รับตั้งรหัสผ่านและรับข้อกำหนดเอง ไม่สร้างรหัสผ่านเริ่มต้น ไม่ยืนยันอีเมลแทนผู้รับ และไม่ลงบันทึก consent แทนเจ้าของบัญชี
- `delete`: รับ UUID หนึ่งบัญชีที่มีโปรไฟล์สมาชิก MAXMUXSIX และเรียก Auth Admin deletion ลบ Auth user จริงและโปรไฟล์ที่อ้างอิงแบบ cascade ไม่ใช่ซ่อนชื่อใน localStorage ไม่จำกัดผู้เรียกว่าต้องเป็นเจ้าของบัญชี และไม่มีข้อยกเว้นสมาชิกที่มีบทบาท admin ตามคำขอทุกบัญชี
- ไม่เพิ่มคำสั่งลบจำนวนมาก ไม่เพิ่มการแก้ role/password/email หรือการอ่านข้อมูลลูกค้าโดยบุคคลทั่วไป
- คง `admin-users`, private role table และ profile RLS เดิม ไม่เปิด anon SELECT/UPDATE/DELETE บนตารางโปรไฟล์ ไม่เปิดสิทธิ์แก้สินค้าให้ผู้เข้าชม
- ข้อผิดพลาด provider แสดงข้อความทั่วไป ไม่สะท้อนอีเมลหรือรายละเอียดภายในกลับสู่รายชื่อสาธารณะ; ไม่อ้างว่าส่งคำเชิญหรือเพิ่มสำเร็จเมื่อ provider ปฏิเสธ

## ข้อจำกัดที่มีอยู่จริง

โค้ดปัจจุบันและบันทึกการตั้งค่าระบุว่ายังไม่มี Custom SMTP และผู้ใช้เคยสั่งว่าไม่ต้องสร้างบริการเพิ่ม เอกสาร Supabase ที่ตรวจในรอบนี้ระบุว่า SMTP เริ่มต้นส่งได้เฉพาะอีเมลสมาชิกทีมโปรเจกต์ จึงยังไม่สามารถรับประกันการเพิ่ม/เชิญลูกค้าทั่วไปด้วยอีเมลได้

แบบนี้ไม่สมัครบริการเมล ไม่ปิด Confirm email ไม่ auto-confirm และไม่เปลี่ยนการเพิ่มเป็นบัญชีที่ไม่มีผู้รับยืนยัน หากยังไม่เชื่อมบริการส่งเมลที่รองรับ ต้องรายงานว่า **การเพิ่มสมาชิกทั่วไปยังติดข้อจำกัดเมล** แยกจากผลทดสอบ list/delete ที่อาจทำงานได้ ไม่อ้างว่าครบทั้งระบบ

แหล่งข้อมูล: https://supabase.com/docs/guides/auth/auth-smtp

การลบไม่รับประกันให้ JWT ที่ออกไปแล้วหมดอายุทันที ต้องตรวจพฤติกรรมจริงของ login, refresh และข้อมูลที่ใช้ session หลังลบบัญชี ไม่เพิ่มตารางส่วนกลางใหม่ที่เชื่อถือ JWT เก่าโดยไม่มีแถวสมาชิกอยู่ และไม่กล่าวอ้างว่าลบข้อมูลคำสั่งซื้อ/สลิปใน localStorage หรืออีเมลที่ส่งไปแล้วด้วย

## ผลกระทบและการกู้คืน

- บุคคลทั่วไปและบอตสามารถลบสมาชิกจริงได้โดยตั้งใจ นี่เป็นผลตามแบบที่ผู้ใช้ขอ ไม่ใช่ข้อบกพร่องที่ถือว่าแก้แล้ว
- การลบบัญชีไม่มีปุ่มย้อนกลับ การสมัครใหม่ไม่คืน UUID, รหัสผ่าน, โปรไฟล์ หรือการอ้างอิงเก่า
- การปิดสวิตช์หรือ rollback function หยุดคำขอใหม่ได้ แต่ไม่คืนบัญชีที่ถูกลบไปแล้ว
- การเพิ่มคำเชิญแบบเปิดอาจถูกใช้ส่งอีเมลรบกวนและใช้โควตา provider ต้องไม่กล่าวว่าข้อจำกัดของ provider ป้องกันการใช้งานผิดทั้งหมด

## การทดสอบและขอบเขตการนำขึ้นจริง

1. เขียน regression tests ให้ anonymous list/invite/delete ผ่านเมื่อสวิตช์เปิด และทุกคำสั่งปฏิเสธเมื่อปิด โดยไม่ต้องมี JWT/role
2. ตรวจว่า response ไม่เปิดเผย PII/secret, ไม่คืน Auth user ดิบ, รับเฉพาะสมาชิก MAXMUXSIX, และคง private profile RLS
3. ตรวจ input ผิด, origin ผิด, provider failure, pagination, ไม่มี bulk operation และ public UI ไม่ให้สิทธิ์แก้สินค้า
4. ทดสอบ UI ที่ไม่มี login ทั้ง desktop/mobile, ยืนยันลบ, retry, keyboard และ race ด้วย provider fixture ที่ไม่ยิงบัญชีจำลองไป production
5. รัน npm test และ browser regression ของระบบสมาชิกเดิม เปลี่ยน expectations เฉพาะการจัดการสมาชิกสาธารณะ ไม่ลบ tests การป้องกันข้อมูลส่วนตัวหรือสิทธิ์แก้สินค้า
6. Hosted smoke test เริ่มจาก read-only และตรวจ disabled/enabled behavior; ไม่เลือกลบบัญชีลูกค้าจริงเพื่อพิสูจน์ระบบ การทดสอบ mutation จริงต้องใช้บัญชีทดสอบที่กำหนดไว้ชัดเจนและการส่งเมลต้องได้รับอนุญาตแยก
7. รายงานผล code/fixture/live แยกกัน และรายงาน SMTP blocker ถ้ายังอยู่ การ push ไม่ใช่หลักฐานว่า GitHub Pages deploy สำเร็จ
